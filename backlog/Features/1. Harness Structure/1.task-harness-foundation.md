# Task 1: Harness Foundation

**Status:** ✅ done  
**Feature:** 1. Harness Structure

## Goal

Establish the one-file-per-tool harness pattern so that all future tools follow a
uniform, mechanically-enforceable structure. Create the skill that enforces the pattern.

## What was done

### Structural changes

- Moved all four existing tool registrations out of `src/server/mcpServer.ts` into
  individual files under `src/tools/`:
  - `src/tools/getActiveFile.ts`
  - `src/tools/getProblems.ts`
  - `src/tools/listWorkspaceFolders.ts`
  - `src/tools/showMessage.ts`
- Created `src/tools/registry.ts` as the single harness assembler.
- `src/server/mcpServer.ts` now calls only `registerAllTools(server, tools)`.

### Tests added

- `tests/tools/_helpers.ts` — shared `makeMockServer` and `makeMockTools` factories
- `tests/tools/getActiveFile.test.ts`
- `tests/tools/getProblems.test.ts`
- `tests/tools/listWorkspaceFolders.test.ts`
- `tests/tools/showMessage.test.ts`
- `tests/tools/registry.test.ts`

Total test count went from 18 to 48 (all passing).

### Documentation added

### Backlog created

## Key decisions

See `docs/harness.md` for the full rationale behind:
- Why one-file-per-tool (isolation, merge conflicts, testability)
- Why the registry pattern (single source of truth for active tools)
- Why `TOOL_NAME` is exported (refactor-safe references)
- Why tool tests mock both McpServer and McpTools (layer separation)
